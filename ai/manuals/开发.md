# 开发手册：跑命令 + 精准编辑 + 内容搜索（开发闭环）

对标开发助理的核心闭环：**搜代码 → 改代码 → 跑命令验证 → 读报错 → 再修**。四步循环直到通过。

## 一、run_command（执行命令行）

```
run_command command="node test.js" cwd="F:\myproject" timeout=120
```

- cmd 语法（Windows）；`cwd` 是工作目录（跑项目命令必传项目根目录）；`timeout` 秒，默认 120 上限 600
- 返回：退出码 + stdout/stderr 合并输出（超长自动归档，按提示 read_file 回读）
- **退出码非 0 = 失败**：stderr 里通常有报错原因，逐行读，改完重跑
- 超时被终止（TIMEOUT）：说明命令长时间不退出（比如起了 dev server 挂着）——这类常驻命令不要等它，改用后台方式跑，或让它跑完打印再退出

### 典型用法
```
node test.js / npm test / pip install requests / git status / python main.py
npm run build / gcc main.c -o main.exe / flutter analyze
```

### 红线（自动硬拦，写了也会被拒）
格式化磁盘、del /f、rd /s、reg delete、shutdown、bcdedit 等系统破坏类命令。删除项目文件用 delete_path（有快照可还原），不要用命令删。

## 二、edit_file（精准编辑，改代码首选）

```
edit_file path="F:\myproject\app.js" old_string="const port = 8080" new_string="const port = 3000"
```

- `old_string` 必须**与文件内容完全一致**（含缩进/空白/换行）——不确定就先 read_file 拿原文
- 命中多处会拒绝：把上下文加长到唯一（比如带上一行函数名），或确实要全改传 `replaceAll: true`
- 找不到原文（count=0）：多半是空白/缩进不一致，重新 read_file 对齐
- 修改前自动备份，可检查点回滚
- **改一行用 edit_file，别用 write_file 整文件重写**——又快又稳不伤其他内容；只有新建文件才用 write_file

## 三、search_file_content（内容搜索，改码前先定位）

```
search_file_content dir="F:\myproject" query="function handleLogin"
search_file_content dir="F:\myproject\src" query="port\s*=\s*\d+" regex=true
```

- 递归全子目录，返回 `文件路径:行号: 命中行`（最多 60 行，超了换更精确关键词）
- 自动跳过 node_modules/.git/dist 等噪声目录和二进制文件
- 默认按普通关键词（不区分大小写），传 `regex: true` 按正则搜
- **改代码前先搜**：函数定义在哪、被谁引用、配置项在哪——搜完再动手，避免改错文件

## 四、本地网页开发预览（browser_* + file://）

写完网页自己看效果，零外部依赖：

```
1. write_file path="F:\demo\index.html" content="<!DOCTYPE html>..."
2. browser_navigate url="F:\demo\index.html"     ← 本地路径自动转 file:///，在 AI 浏览页签打开
3. browser_snapshot                               ← 查 DOM 结构/元素编号
4. screenshot scope:"screen" → view_image          ← 看渲染视觉效果
5. browser_fill / browser_click                    ← 测表单交互
6. 发现问题 → edit_file 修 → browser_navigate 刷新 → 再验证
```

注意：file:// 页面里 fetch/ajax 跨域受限（浏览器安全策略）——纯静态页面/内嵌数据没问题；要跑后端接口的页面先用 run_command 起 dev server，再 browser_navigate http://localhost:端口。

## 五、标准开发循环（忘了吗就回来读）

```
① search_file_content 定位相关代码
② read_file 读上下文（大文件分段）
③ edit_file 精准修改
④ run_command 跑测试/编译
⑤ 退出码 0 → 完成；报错 → 读 stderr 定位 → 回到②
```

多文件大改动先 task_plan 建清单；同文件多处修改逐处 edit_file（每处一个 old/new），不要图省事整文件重写。

## 五·补、dev_server 与 git（长驻进程 + 版本底座）

**dev_server（长驻开发进程）**：`npm run dev`、`uvicorn main:app`、`mvn spring-boot:run` 这类跑起来不退出的命令，**禁止用 run_command**（会被超时掐断），用 dev_server：

```
dev_server action=start command="npm run dev"     → 返回 id + 启动日志尾部（等 2.5 秒抓端口就绪）
dev_server action=list id=ds_xxx                  → 看最新日志尾部（30 行）
dev_server action=stop id=ds_xxx                  → 停止（taskkill 进程树）
```

用户说"跑起来我看看"= start 后把端口地址告诉用户；改完代码看效果 = list 看热重载日志有没有报错。

**git（版本底座）**：改代码前 status 看现场，交付前 commit 留底：

```
git action=status                → 分支+改动清单（porcelain）
git action=diff path=src/app.js  → 改动统计 + diff（可只看某文件）
git action=commit message="修复登录态丢失：token 未随刷新持久化"   → 自动 add 全部+提交
git action=log                   → 最近 20 条
```

铁律：commit 的 message 说**为什么改**不是改了什么文件名；不是 git 仓库时提示用户要不要 git init，不擅自 init。

**报错行号跳转**：run_command 失败时输出尾部有"—— 报错位置 ——"（绝对路径:行:列），用户端卡片里可点击直达工作台对应行——汇报时直接引用该位置，别让用户自己找。

## 六、Bug 处理规范（修不动主动问，别闷头硬修也别假装修好）

run_command 失败（退出码非 0）时的**分级升级**：

| 轮次 | 动作 |
|---|---|
| 第 1 次失败 | 读 stderr 定位 → 明显的错（语法/路径/拼写/缺依赖）→ 直接修 + 重跑验证 |
| 第 2 次失败 | 换思路再修一次（换实现方案/搜 web 查报错/换依赖版本） |
| 第 3 次仍失败 | **必须 ask_user**：贴关键报错原文 + 已尝试的两条路 + 你的判断建议，让用户拍板（继续修/换方案/先绕过） |

**红线**：①修不动就说"完成了"= 最严重的失信（用户一跑就炸）②无限重试空转烧步数 ③修好了必须说明改了什么（edit_file 的 old→new 摘要）+ 验证证据（退出码/输出关键行），禁止无证据宣称"已修复"。

## 六·补、顺手修原则（修 A 发现 B，顺手修掉，别装看不见）

上面的分级升级管的是"**同一个 bug** 修不动怎么办"；这一节管"**别的 bug** 怎么办"——写代码或修 A 的过程中发现了 B 的 bug，**禁止视而不见**：

| B 的规模 | 动作 |
|---|---|
| 小 bug（同文件/同链路、方案明确、几行能修好） | **顺手修掉**，修完在汇报里单列"顺手修了什么"（一句带过，不用小题大做） |
| 中 bug（影响面清楚但要改好几处） | 先把 A 修完交付，汇报末尾列出 B（现象+根因+建议方案），问用户要不要现在修 |
| 大 bug（架构级/影响面不明/牵一发动全身） | 不动它。汇报末尾明确预警（现象+风险+你的判断），等用户拍板 |

**判断口诀**：几行能修就顺手修，十几行先汇报再修，伤筋动骨只预警不动手。注意两点：①顺手修的范围仅限用户自己项目里的 bug，系统文件/无关项目不动 ②顺手修也必须走 edit_file + 验证，不许"我看了一眼应该没问题"。
